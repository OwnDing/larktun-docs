# Larktun Common Issues

This guide is organized around symptoms you actually observe when connecting to devices in your Larktun network, along with the fastest verification commands and fixes for each layer.

## Recommended Troubleshooting Order

Always isolate problems from the control plane down to the data path so you do not waste time debugging the wrong layer:

1. **Check `Nodes`**: confirm both source and target devices are **Online** in the same tenant.
2. **Check `ACLs`**: verify your user/group, target device/CIDR, and exact port are permitted.
3. **Check `Routers`** (subnet scenarios only): confirm the CIDR route is advertised, approved, and accepted on the client.
4. **Check `Derper` & path quality**: inspect whether traffic is direct P2P or relayed and verify latency.

### Quick CLI Diagnostic Commands

On Linux, macOS, Windows, or OpenWrt endpoints, these three commands surface most root causes in seconds:

```bash
# 1. Verify login state, assigned private IP, and peer online status
larktun status

# 2. Check whether traffic to a target peer is direct P2P or relayed via DERP
larktun ping <target-ip-or-hostname>

# 3. Inspect NAT type, UDP reachability, and nearest DERP relay latency
larktun netcheck
```

## 1. Access Denied by ACL

### Symptoms
- Connection refused or permission denied even though both devices show **Online** in **Nodes**.
- One user or device can connect, while another user in the same tenant is blocked.
- Ping works, or one port works, while SSH (`22`) or RDP (`3389`) fails.

### How to Fix
1. Open **ACLs** and verify that `src` matches your exact account (with trailing `@` where required), user group, or device tag.
2. Verify `dst` points to the active node (not an older duplicate device with a similar hostname) and includes the right port suffix (`:22`, `:443`, `:3389`, `:5001`, or `:*`).
3. Confirm you clicked **Save / Publish** after editing, wait 5–10 seconds for policy propagation, and retry.
4. Check the target host's own OS firewall (`ufw`, `firewalld`, Windows Defender Firewall) to make sure the service listens on the private interface rather than `127.0.0.1` only.

## 2. Device Shows Offline or Fails to Connect

### Symptoms
- The target machine appears **Offline** in **Nodes**.
- The device briefly comes online after login, then drops or times out repeatedly.

### How to Fix
1. On the target machine, run `larktun status` (or open the desktop/mobile app) to confirm the daemon (`larktund`) is running and signed in.
2. Confirm the Auth Key used for headless login has not expired or been revoked, and verify `--login-server=https://hs.larktun.com` was spelled accurately.
3. Check the system clock on routers, NAS devices, and embedded Linux hosts—large clock skew causes TLS handshake failures against the control plane.
4. Test from another network path (for example switching between Wi-Fi and cellular) to rule out a restrictive local firewall blocking outbound HTTPS/UDP.
5. Restart the client service (`sudo systemctl restart larktund` on systemd Linux) and refresh **Nodes**.

## 3. Subnet Resources Unreachable (Subnet Router Scenarios)

### Symptoms
- You can `ping` or SSH into the subnet router node itself, but cannot reach devices behind it (such as `192.168.6.10`).

### How to Fix
1. In **Routers**, confirm the subnet CIDR (for example `192.168.6.0/24`) is both visible and switched **On** (approved).
2. In **ACLs**, verify there is an explicit `accept` rule allowing your `src` to reach `192.168.6.0/24:<port>` or `192.168.6.0/24:*`.
3. On the **client** trying to reach the subnet, confirm route acceptance is enabled (`sudo larktun set --accept-routes`).
4. On a Linux or OpenWrt **subnet router**, confirm kernel IPv4 forwarding is enabled (`sysctl net.ipv4.ip_forward` should return `1`) and the router's firewall permits forwarding between the Larktun interface and LAN zone.
5. Verify your local Wi-Fi network does not use the exact same CIDR as the remote subnet (overlapping `192.168.1.0/24` routes cause traffic to stay on the local LAN).

## 4. High Latency, Laggy Remote Desktop, or Intermittent Disconnects

### Symptoms
- Sluggish RDP/WebRTC frame updates or SSH typing lag.
- Occasional session drops, especially during evening peak hours or across different ISPs.

### How to Fix
1. Run `larktun ping <target>` to see whether packets travel **direct** or via a **DERP relay**.
2. If traffic is stuck on a distant relay due to symmetric NAT, check whether UDP outbound traffic is permitted or switch to a geographically closer relay region in **Derper**.
3. For heavy daily remote desktop workloads, upgrade from the default shared relay to a **dedicated relay** or attach a **user-managed relay** closer to your servers (see [Deployment Modes and Configuration](../getting-started/install-and-configure)).
4. If using iOS RDP in bitmap fallback mode, enable RemoteFX on Windows (see [Optimize iOS Remote Desktop: Enable RemoteFX](../topics/optimize-ios-rdp-remotefx)).

## 5. Higher-Than-Expected Client Usage or Background Interruptions

### Symptoms
- Higher CPU/memory usage than normal on a desktop endpoint.
- Repeated reconnect notifications.

### How to Fix
1. Avoid scripts or manual loops that repeatedly execute `larktun up` when the tunnel is already connected.
2. Close stale foreground remote desktop/file transfer windows when finished.
3. Enable quiet background mode (minimize to system tray) in client settings.

## 6. User-Managed Relay Unreachable

### Symptoms
- Connections degrade or drop immediately after adding a custom DERP relay.

### How to Fix
1. In **Derper**, double-check `hostName`, `ipv4`, `derpport` (TCP), and `stunport` (UDP).
2. Temporarily keep `omitDefaultRegions: false` so traffic can fail back to default platform relays while you debug TLS certificates and firewall rules on your custom DERP host.
3. Verify externally with `curl -I https://<hostName>:<derpport>` and confirm UDP `3478` is open in your cloud security group.

## 7. DNS Resolution or Alibaba Cloud Private DNS Conflicts

If you run Larktun alongside Alibaba Cloud ECS / internal DNS and see unexpected lookup failures, follow our dedicated guide: [Resolving Larktun and Alibaba Cloud DNS Issues](./larktun-alibaba-cloud-dns).

## When to Contact Support

If the issue persists after completing the checklist above, include these details so support can diagnose it immediately:

- Exact timestamp (with timezone) when the failure occurred
- Your account email and tenant name
- Source and target device names (and OS / client version)
- Target protocol and port (e.g., SSH 22, RDP 3389, HTTPS 443)
- Output of `larktun status` and `larktun ping <target>` (redact any Auth Keys)
