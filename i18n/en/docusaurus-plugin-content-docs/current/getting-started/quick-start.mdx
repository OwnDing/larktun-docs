# Larktun Quick Start

This guide walks you through your first end-to-end setup in the Larktun SaaS console: enrolling your first devices, approving subnet routes, verifying tenant members, configuring least-privilege ACLs, choosing a relay strategy, and testing private connectivity.

> All console screenshots below are served in `webp` format for fast loading.

## Prerequisites

Before you start, make sure you have:

- A registered Larktun account at [larktun.com](https://larktun.com/auth/register) (every account gets an isolated personal tenant with **up to 5 free devices**).
- At least two devices to test private connectivity (for example, your laptop/phone plus a Linux server, NAS, home PC, or OpenWrt router).
- If you plan to use a user-managed DERP relay later, one publicly reachable host with open HTTPS/STUN ports.

## 1. Nodes: Onboard and Manage Devices

Open the **Nodes** page in the console to manage devices enrolled in your tenant.

From this view you can:

- Generate one-time or reusable **Auth Keys** for headless servers, NAS units, Docker containers, or routers.
- Inspect online status, assigned private IPv4 address (`100.64.x.y`), and MagicDNS name.
- Rename raw `HOSTNAME` entries into readable labels such as `home-nas`, `dev-macbook`, or `prod-gateway`.
- Remove stale or decommissioned devices immediately to revoke their network keys.

![Nodes page (device details, remove, rename)](/img/view/nodes.webp)

### Enroll Your First Devices

Install the Larktun client on your target platforms:

- **Desktop (Windows / macOS / Linux)**: Download from [larktun.com/download](https://larktun.com/download) or follow [Desktop Client Operations](./desktop-client-operations).
- **Linux server / ARM64 NAS**: Run the one-line installer from [Install Larktun on Linux](./linux-install-larktun) or [Install Larktun on a NAS](./nas-install-larktun), then authenticate with your Auth Key:

  ```bash
  sudo larktun up --login-server=https://hs.larktun.com --auth-key=<Your Auth Key>
  ```

- **OpenWrt router / Docker / iOS / Android TV**: See [OpenWrt](./openwrt-install-larktun), [Docker](./docker-login-larktun), [iOS App Overview](../introduction/ios-app-overview), and [Android TV](./tv-install-larktun).

Refresh **Nodes** until both devices show as **Online**.

## 2. Routers: Approve Subnet Routes

If one of your online nodes advertises a local LAN CIDR (for example `192.168.6.0/24` to expose printers, IP cameras, or a NAS that cannot run a client directly), open **Routers** to review and approve the advertised route.

Recommended practice:

- Approve only the specific subnets you intentionally want reachable from the mesh.
- Avoid overlapping CIDR ranges across multiple sites inside the same tenant.
- Test reachability right after toggling approval, and remember that ACL rules must also allow traffic to that subnet.

![Routers page (subnet route approval)](/img/view/routers.webp)

For the complete command-line and ACL walkthrough, see [Approve Subnet Routes](./approve-subnet-routes).

## 3. Users: Verify Tenant Membership

The **Users** page displays all accounts belonging to the current tenant so you can audit ownership clearly.

Recommended practice:

- Confirm each user identity matches the expected account before referencing it in ACL rules.
- Review and remove departed team members or unused test accounts regularly.

![Users page (tenant user list)](/img/view/users.webp)

## 4. ACLs: Configure Access Control Policy

The **ACLs** page defines exactly which users, groups, or device tags can reach which targets and ports. By default, follow least privilege rather than opening every port permanently.

Built-in capabilities:

- Ready-to-use ACL templates for fast initial validation.
- Visual policy editor for day-to-day maintenance.
- Raw JSON editor for fine-grained port rules, `hosts` aliases, `tagOwners`, and `autoApprovers`.

![ACLs page (visual + JSON editing)](/img/view/acls.webp)

For example, once two devices under your account are online, allow your account to reach its own devices first, test `ping` or `ssh` to the target's private `100.64.x.y` address, and then narrow the destination ports (such as `:22`, `:443`, or `:3389`).

## 5. Derper: Configure Relay Servers

When NAT traversal succeeds, Larktun establishes a direct encrypted WireGuard path between peers. When restrictive firewalls or symmetric NAT block direct UDP, traffic falls back automatically to a DERP relay.

Use the **Derper** page to choose your relay tier:

- **Default shared relays**: Included automatically for all free and paid accounts with zero setup.
- **Dedicated VIP relays**: Available for paid plans that require lower jitter and reserved capacity.
- **User-managed relays**: Attach your own self-hosted DERP nodes via the visual form or JSON config for regional routing or compliance isolation.

![Derper page (relay server settings)](/img/view/derper.webp)

## 6. Me: Verify Account and Tenant Context

The **Me** page shows your active account profile, tenant details, and quota usage so you can confirm you are operating in the right workspace.

![Me page (personal profile)](/img/view/me.webp)

## Verify Your First End-to-End Connection

Before deploying more services, validate one concrete path:

1. Copy the target device's private IP from **Nodes** (for example `100.64.0.5`).
2. From your laptop or the Larktun mobile app, run a connectivity check (`ping 100.64.0.5`) or open SSH / RDP / a private Web dashboard.
3. Confirm the connection succeeds without opening any inbound ports on your router or cloud security group.
